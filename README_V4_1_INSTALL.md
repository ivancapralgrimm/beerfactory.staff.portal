# BFStaff r40.6 v4.1 — временная совместимость без серверной миграции

Основа: установленный v4 AUDITED; рабочая ветка `r40.6-attestation-editor`, HEAD при аудите `b827444e905f8b36cf0f2261e4e0cdb7b07e71be`.

## Что исправлено

1. При подтверждённом PostgREST `PGRST202` (новой RPC ещё нет) загрузка аттестации переходит на СТАРУЮ `get_attestation_bank` только для исходных canonical bar/kitchen/wine/service с BF. Никакие произвольные категории не классифицируются автоматически.
2. Такой банк существует только в памяти, никогда не кешируется в IndexedDB как настоящий v3. При появлении SQL v3 кнопка обновления или перезагрузка приложения вернёт новый серверный банк.
3. Ошибки авторизации/сети не являются основанием перейти на старую RPC. При несовместимом legacy-ответе отображается ошибка, а не неполный/выдуманный билет.
4. Пока сервер не обновлён, сотрудники видят предупреждение о временном режиме; владельцы/админы видят в редакторах чёткое сообщение о необходимости миграции.
5. Независимые билеты, BB и общие вопросы не эмулируются до серверного обновления. Задействованные старые 4 BF билета работают в read-only режиме.

## Как установить с телефона

Архив является **ДЕЛЬТОЙ**, полную v4 повторно загружать не нужно. Распакуй архив в «Файлы». Только 8 файлов из `package.json`, `src/` и `tests/` нужно разложить в СООТВЕТСТВУЮЩИЕ пути ветки `r40.6-attestation-editor`. Семь заменить, `tests/attestation-staged-upgrade-v4.test.cjs` создать. Файлы из `docs/` и MANIFEST в GitHub загружать не нужно. Перед заменой проверить старые SHA в MANIFEST, чтобы не стереть изменения после аудита.

**Не применять/не повторять SQL автоматически.** Миграция `supabase/migrations/20261012120000_attestation_independent_tickets_v3.sql` уже в ветке, но отсутствует в production. Для полной функциональности нужны её проверка в тестовой базе и отдельное разрешение владельца на production.

Полный npm-тест и реальные браузерные сценарии после загрузки v4.1 пока НЕ исполнены, подтверждение release-ready отсутствует.

Сначала тестовая БД, затем с разрешения production миграция, затем новый клиент/деплой. Никогда не обновляй production SQL по этой инструкции без явного согласия владельца. Вопросы, историю, outbox и старые миграции сохраняем.
