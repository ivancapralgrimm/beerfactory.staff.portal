# BFStaff independent review protocol — r40.6 v4.8

## Проверено

- Проблема устаревшего чтения подтверждена по исходному коду реального Vercel serverless `/api/recipes/menu` (старый `Cache-Control: public, s-maxage=30, stale-while-revalidate=300`).
- По маршруту `config.recipeApiBase + '/menu'` Vercel preview отдаёт корректный JSON `recipes` из NocoDB; путь существует.
- Старый `recipe-admin-api.ts` запускал fire-and-forget `loadRecipes({ force:true })` после POST/PATCH/DELETE, при том что оба UI-экрана делают `await reload()`. Это приводило к конкуренции.
- Сетевые операции **записи не ретраятся**; одна команда пользователя соответствует одному PATCH.
- Отдельный `requestVersion` предотвращает запоздавшую публикацию данных из старого запроса в hook.
- Внесённые изменения не требуют изменений Supabase, НocoDB или Cloudflare Worker.
- `node --test`: 7 из 7 сценариев прошло (нормализация BF/BB, актуальный/архив, заголовки, отказ Worker, сохранение, race).

## Риски / границы проверки

- НЕ выполнялся реальный авторизованный PATCH существующих рецептов. Нельзя утверждать, что Cloudflare Worker и NocoDB не имеют собственных нестабильностей.
- НЕ запускался полный `npm run build` против всего приватного репозитория. Только синтаксический аудит и изолированные тесты затронутых файлов.
- Меню теперь читается сервером Vercel без CDN-кэша. При ~50 сотрудниках и клиентском TTL 5 минут объём запросов ожидается умеренным, но нагрузку следует наблюдать.
- При проблемах сети `loadRecipes(force: true)` по прежнему может использовать офлайн-копию. Отдельную диагностику недоступности Worker нужно делать по ответу записи/логам.

**Вердикт: PASS WITH RISKS**, ожидается эксплуатационная проверка после деплоя. Это не мнение внешнего независимого агента: второй проход проверки проведён по отдельному протоколу.
