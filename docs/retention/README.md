# Хранение истории и очистка ветки

Пользователь подтвердил:аттестации — по сотруднику и билету,смены — по должности,журнал — по разделу. Для удаления одновременно нужны два условия:записи строго больше60дней и она не входит в10последних в своей группе. Недавние записи сохраняются все,а не только10.

## Установлено на сервере

Миграция `20261103194544_r407_history_retention_60d_floor10` применена к общему Supabase. Один активный job `bfstaff-history-retention` запускает приватную функцию ежедневно в03:15НСК (`15 20 * * *`,cronGMT),после окончания смены. Исполнение — postgres,никакой локальный ПК или платный сервис не требуется. Старое месячное задание убрано;его private wrapper теперь также соблюдает защиту последних10 и нерешённых заметок.

| История | Группа и ограничение |
| --- | --- |
| Аттестации |10последних по user_id + ticket ID;для старых безID — по сохранённому названию. Снимки результатов живут вместе с сохранённой попыткой. |
| Завершённые/истёкшие смены |10последних по должности. Активные,незавершённые состояния и текущие даты защищены. Снимки галочек удаляются только вместе с выбранным старым состоянием. |
| Журнал изменений |10по «Персонал и доступ» и «Портал». Служебные итоги смен — отдельно по должности,когда она указана. |
| Решённые заметки |10по категории. Нерешённые и противоречивые статусы защищены. Отметки ознакомления удаляются каскадом только вместе с удаляемой заметкой. |
| Технические запуски cron |10завершённых по каждой задаче. Текущие запуски сохраняются. |

Возраст считается с учётом окончания/разрешения/истечения и даты получения сервером:старый результат,недавно загруженный офлайн,не исчезает сразу. Заголовки смен удаляются только без сохраняемых состояний,заметок и сообщений;для прежних чек-листов тоже действует минимум10. Вопросы,версии вопросов,актуальные статьи,рецепты,фотографии,аватары и профили сохраняются.

`private.cleanup_portal_history()` по умолчанию только считает кандидатов;реальная очистка требует явногоfalse. Функции недоступны anon/authenticated/service_role;использует их только внутренний cron/операторpostgres. Параллельные уборки защищены транзакционной блокировкой.

Проверено в live:все3тела функций совпали с reviewed SQL,ownerpostgres,права закрыты. Read-only preflight вернул0кандидатов. Явный первый запуск также удалил0строк — сейчас нет истории,подходящей под оба условия. Расписание и подтверждение находятся в `receipt.json`,исходные определения/схема — в `before-state.json`. Существующее03:00НСК задание финализации смен сохранено.

## Дни рождения

Существующее правило уже точное:за3дня до даты,сам день и ещё1день после. Например,для6ноября показ идёт с3по7ноября включительно. `days_until`3,2,1,0,-1. Отдельный SQL-тест проверяет весь календарный интервал,переход года и29февраля;ложное смещение на4дня до/2после исключено. Повторно заменять уже правильную live функцию не требовалось.

Старые capture→supplement→findings runners продолжают генерировать собственные промежуточные файлы;эталон `profile-avatar-size/after.json` сохранён. ## Проверки и отмена расписания

`npm run test:retention`:13сценариев точного SQL (границы60дней,группы,FKкаскады,свежая синхронизация,нерешённые заметки,права,старыйwrapper,cron,идемпотентность) и3календарных сценария. Проверка включена в CI. Тесты проекта,production/PWA build,общий e2e,Chromium/LinuxWebKit и Unslop/Hallmark повторяются после очистки. Никакая фикстура не выдаётся за проверку production входа/устройства.

Чтобы остановить будущую очистку,оператор может выполнить `select cron.unschedule('bfstaff-history-retention');`. Прежнюю месячную задачу включать не нужно:она не соблюдала новую политику. Остановка расписания не восстанавливает уже удалённые записи;сейчас первый запуск удалил0. Миграции не переигрывать и не удалять из истории. Материалы и версии вопросов не подвергались физической очистке.
