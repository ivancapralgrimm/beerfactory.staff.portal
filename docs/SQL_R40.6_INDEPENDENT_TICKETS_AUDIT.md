# SQL-аудит независимых билетов r40.6

Проверяемый файл: `supabase/migrations/20261012120000_attestation_independent_tickets_v3.sql`.
**Миграция подготовлена в рабочей копии и проверена только в изолированном PostgreSQL WASM. Production/remote Supabase не использовался.**

## Целостность и перенос

`attestation_questions` остаётся единственной физической таблицей банка. Новых таблиц копий, назначений по должностям/сотрудникам нет. Вопрос содержит отдельные `knowledge_type` и `venue`; `category_id` сохраняется для обратной совместимости и исторического происхождения. Отбор v3 использует тип/заведение, а не этот ID.

Канонические bar/kitchen/wine/service получают свои типы; надёжно совпадающие названия четырёх прежних типов классифицируются. BF — default старых/новых записей; common допускается в BF и BB, BB-only не выдаётся BF, BF-only — BB. Билет common получает только common. Незнакомые старые категории сохраняются, остаются черновиками до ручного выбора; пустое «Бистро» не удаляется и автоматически не классифицируется.

ID, планы, вопросы, архивы и quiz_attempts не очищаются. Начальная проверка активных планов останавливает миграцию при несовместимом наборе. Старые миграции не редактировались и не должны повторно применяться. Подготовленная миграция предназначена для однократного выполнения в транзакции через обычный migration runner.

## Найденные ошибки и исправления

1. **42P13 при CREATE OR REPLACE**: имя параметра существующей `private.attestation_question_snapshot` изменялось с p_question на q. Оставлено исходное имя; DROP не используется, зависимости и привилегии функции сохраняются.
2. **Потеря типа/venue при переименовании**: save_category_v3 подставлял bar/bf для любого существующего билета. Оmitted fields теперь сохраняют старые значения, в том числе NULL у черновика; timestamps обновляются.
3. **Зависимость вопроса от типа служебной категории**: save_question_v3 требовал совпадения типа билета-источника с типом вопроса. Оставлена проверка существования источника. Переклассификация билета не блокирует правку вопроса исходного типа.
4. **NULL-массивы и нормализация ID**: SQL three-valued logic пропускала NULL; settings мог очистить планы черновиков. `IS DISTINCT FROM` отклоняет NULL/неверный JSON; дубли после btrim отклоняются до записи.
5. **Legacy-мутации**: старые RPC могли создать вопрос без knowledge_type, сохранить неверный тип при переносе, проверять ёмкость только исходной категории и блокироваться в обратном порядке с v3. Старые entrypoints сохранены; вопрос/статус перенаправляются к v3, legacy settings/category берут singleton-lock до остальных записей и проходят v3-guards.
6. **Legacy-read несовместим с общими ID**: старый валидатор запрещает повтор ID между категориями. Адаптер v2 выдаёт прежние совместимые BF-билеты из их исходных записей, с проверкой ёмкости по плану; новые независимые/BB/common/точные квоты обслуживает v3. Проверяется фактический старый валидатор, а не только присутствие строк SQL.
7. **Округление изменяло зачёт**: 39/49 отображается как 80%, но меньше точных 80%; старый сервер засчитывал, клиент — нет. Сервер теперь сравнивает correct*100 >= total*threshold и округляет только отображаемый score.
8. **Duplicate-response и конкуренция**: сохранён pass_percent в duplicate-response; lookup+insert защищены advisory transaction lock по user/attempt и прежним уникальным индексом с ON CONFLICT. Подтверждение не создаёт вторую строку при повторе того же ID.
9. **Проверки сохранения результата**: отклоняются неизвестные категории, NULL/неверные JSON, неверные диапазоны/время и несуществующие ревизии; непустой список ревизий имеет длину total и уникальные ID. Историческая ревизия принимается после редактирования/архива. Старый пустой список допустим для совместимости.

## Безопасность

В public RPC SECURITY DEFINER нужен для существующего RPC-only доступа к закрытым таблицам. Установлен пустой search_path, таблицы и auth.uid квалифицированы. Новые write/editor-read RPC вызывают прежний `private.attestation_is_admin()`; user-read требует существующий активный профиль. Owner/Admin определяются прежними полями, а не user_metadata/должностью. Новые private helpers закрыты для PUBLIC/anon/authenticated; public v3-функции закрыты для PUBLIC/anon и имеют EXECUTE для authenticated. Табличные права, RLS, профили, Auth и Edge Functions не ослаблены.

Проверены SQL-вызовы как anon, staff, owner, admin, inactive и отсутствующий профиль. Это исполнение серверных guards на синтетических claims; не проверка настоящих JWT/PostgREST.

## Квоты и группы

Активный билет имеет полный план ровно questions_per_test. Каждый раздел имеет достаточно уникальных group_key; группа не может занимать два выбранных раздела того же билета. Общая ёмкость проверяется по группам, не по строкам вариантов. Для точной квоты сервер считает минимальное/максимальное число специфичных групп по каждому разделу и сравнивает общую квоту с суммой диапазонов. NULL сохраняет прежний свободный выбор; 0 означает все common; common-билет допускает только NULL/0. Пересекающиеся common/specific варианты одной группы не дают два места.

Изменение/архив вопроса, классификации билета или плана проверяет все активные билеты. Невалидная транзакция откатывается вместе с ревизиями и снимками. Отложенные constraint-trigger защищают итог целой транзакции, включая legacy DELETE + INSERT плана.

## Исполнение и ограничения

`npm run test:attestation:sql`: exit 0; 27/27 PASS, 0 FAIL, overlay=false. PostgreSQL 18.3 (PGlite 0.5.8). SQL SHA256: `198aa0bad269c5c83259e59a5df379ae52b1feb36f686fc0cb887943ee235567`. Настоящий валидатор legacy-клиента загружается командой `git show` из исходного SHA; проверяет ответы RPC после изменений. Лог: `sql-final.log`.

`tests/attestation-sql-v3.mjs` загружает шесть фактических старых миграций и синтетическую минимальную auth/profiles/quiz_attempts-схему. В памяти создана обезличенная тестовая база; сетевых URL, ключей и production-подключений нет. Применяется настоящий финальный SQL, workaround/overlay не использованы. Проверяются сохранность IDs/counts/history/Bistro, классификация, ACL, общий источник, квоты/архив/rollback, группы, ревизии, legacy и результаты.

Важные ограничения: PostgreSQL PGlite — один сеанс, версия 18.3; целевой Supabase может работать на другой версии. Не проверены многосессионные гонки, полный проект, реальная схема/grants/triggers вне миграций аттестации, PostgREST и производительность. Миграция не заменяет database backup/read-only preflight.

**Оценка не стала доверенной серверной оценкой.** Старый API принимает агрегаты и офлайн-порог от клиента. При допустимых total/correct/pass_percent клиент способен представить вымышленный результат; пустой список ревизий остаётся допустимым. Сервер не получает ответы и аутентифицированный снимок билета, поэтому не может проверить истинность, квоту/принадлежность исторического билета и старый порог. Такой протокол требует отдельного изменения контракта и отдельного QA; существующий контракт в этой задаче сохранён.

Для production остаются обязательны тестовый Supabase той же версии/схемы, параллельные транзакции, реальная сверка вопросов/истории и отдельное разрешение владельца. Исполнение в production не разрешено и не выполнено.
