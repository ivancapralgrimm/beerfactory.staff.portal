## Первый вход: подтверждённая причина и подготовленное исправление

В живых логах повторяется последовательность: внутренний `login_rate_limit_allowed` получает401, при этом второй параллельный запрос получает200; `staff-login` переводит эту техническую ошибку в429. Следующий ручной вход проходит200. Примеры UTC:2026-11-03 15:14:13→15:14:17,16:43:09→16:43:11,18:02:33→18:02:35,18:06:45→18:06:49. Секреты, пароли и персональные сетевые данные в пакет не включены.

Подготовлены `supabase/functions/staff-login/index.ts`, `name-identity.ts`, `rate-limit.ts`:

- Только read-only проверка лимита повторяется один раз при401/408/5xx/сбое транспорта; каждый запрос ограничен4секундами.
- Реальный boolean false сразу сохраняет429. Лимиты6/30, проверка пароля, защита владельца и права не ослабляются.
- Постоянный сбой возвращает503 `login_unavailable`, не маскируется под неверный пароль/реальную блокировку.
- Не повторяются проверка пароля, выдача токенов, записи и весь POST входа.
- В пакет входит ранее согласованный серверный разбор имени/фамилии в любом порядке. Текущая live v8 пока ищет только в прямом порядке.
- Клиент и раньше читал FormData прямо из DOM. Добавлена синхронная защита от нескольких отправок; заполнение без input/change-событий проверено отдельно.

**Edge Function не развёрнута.** До отдельного разрешения на её обновление причина первого429 остаётся в общем backend; публикация одного frontend-коммита её не устраняет.
